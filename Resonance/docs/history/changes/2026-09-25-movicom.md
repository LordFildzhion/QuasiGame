# 2026-09-25 — native x64 Movicom service

Status: implemented and deployed; extended recording and physical unplug/replug acceptance passed. Current contract: [Movicom](../../components/movicom.md). This continues the [reference-software investigation](../investigations/movicom-20260925.md), not a replacement for its evidence.

## Scope and delivered behavior

Added `R:/src/movicom`, a native x64 Qt 6 service using the installed System32 FTDI D2XX driver and the recovered MoviEEG frame protocol. No x86 broker, MoviEEG/KARDi2 DLL, Python runtime or new kernel driver is required by the service. USB identity is the exact Movicom description plus VID/PID and selected serial, not COM number or the first FTDI adapter.

The standard Configurator panel contains Device, fixed 500 Hz rate, block size, CED file and eight selectable channels. Acquisition is against REF; unsupported impedance/mode/gain/trigger controls are absent. Diagnostics are readable in the same 300 px column. Parameter descriptions, locks, malformed-preset refusals and physical-input metadata are implemented and tested.

Worker acquisition, CRC/parser recovery, signed 24-bit conversion to volts, NaN gap rows, duplicate rejection, minimum-loss diagnostics, host timestamps, fixed nominal rate and per-channel clipping counters are documented in the component. Start waits for valid frames; Stop drains/releases the device and publishes the final partial software block. CED and channel changes apply at the next Start.

## Defects found by acceptance

1. **Headless discovery retry never started.** `StreamPool` was constructed before `QCoreApplication` and its constructor attempted to start a timer without an event dispatcher. A subscriber requested before the publisher existed could wait forever. The new late-publisher regression failed on the old core (`discovery-before.log`) and passes after starting the timer on the first discovery request.
2. **Final partial block could disappear at TCP shutdown.** A worker-only assertion passed, but a real TCP subscriber missed the final short block. `OutputStream::close` now queues closure after sends and retains the publisher capsule until closure runs. The regression failed before this change (`software-tests-04.log`) and now passes.
3. **Initial presets raced asynchronous scanning.** Block size and saved serial were refused during initial scanning. Host settings remain editable during scanning (Start is unavailable there), and a requested serial is preserved until discovery completes, including when absent. It never selects another amplifier silently.
4. **The amplifier sometimes ignored Start/Stop commands.** An accepted FTDI write did not guarantee that firmware acted. The original DLL retries D1 DD. The initial native implementation permitted three attempts in three seconds; physical reconnection acceptance required the longer bounded startup window described below. It does not retry an established stream. Stop is verified by draining data to a quiet interval, with bounded repeated D0 DD. The previous latency timer is restored on release.
5. **Old bytes crossed a rapid reopen.** `restart-wire.3.bin` contains 24 leading bytes and an old valid counter-22 frame before the new counter-zero frame. A fixed short pause or purging input alone was insufficient. Verified Stop/drain **before closing as well as after reopening** eliminated this in the 100-cycle campaign. Earlier failed variants remain in evidence; they are not accepted results.
6. **Cancellation while publisher creation was queued.** A cancelled publisher is moved to the application thread until the queued creation/closure finishes, preventing its worker's immediate destruction from invalidating StreamPool's pending raw pointer. A dedicated test destroys the worker thread before allowing publisher creation to run.
7. **USB rediscovery did not establish amplifier readiness.** The first unplug run exposed a QA-script ordering error: it sent Start while a further rescan was pending. The helper now waits for the specific scan to enter and leave the service state machine. In `physical-reconnect02`, Start then reached the worker but all three commands produced no frames before its three-second deadline. A later unchanged, settled-device run passed (`postplug-settled`). The final worker permits up to twenty Start commands at one-second intervals within twenty seconds, with a cancellable Starting state; it still requires valid data before Running. Publisher creation retains its separate three-second deadline and established-stream silence remains one second. Software tests cover delayed valid data, the full bounded timeout and cancellation during this wait. Final physical acceptance is recorded below.

Two early integration-script mistakes (sending an array through a single-parameter FFI call, and requesting a non-reconnecting Recorder slot before it was initialized) were corrected. An initial packaged Recorder run could not initialize Qt because the ordinary distribution lacks the offscreen QA plugin. Its exact test-owned process was closed before recording started. The rerun supplies the matching Qt 6.11.2 offscreen plugin in the **evidence directory only**, records its hash, and still loads normal Qt DLLs from the packaged runtime. No operator window is needed for acceptance.

## Remaining physical acceptance limits

No known-amplitude input calibration, clean second-PC driver installation, human EEG quality assessment or live P300 accuracy test was performed in this implementation campaign. USB error/disconnect/silence recovery is tested with injected transport failures and physical unplug/replug; normal physical reopen is tested repeatedly. Host delivery timing and nominal 500 Hz are not calibrated trigger timing. Six-bit counter ambiguity and abrupt-process-death cleanup limits remain explicit.
