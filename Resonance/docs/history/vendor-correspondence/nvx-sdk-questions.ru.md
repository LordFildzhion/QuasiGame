## 1. ⚠ На 5 кГц теряется 10,7 % отсчётов, и это не наше ПО

**Самый важный вопрос и единственный, который блокирует эксперименты.**

На частоте 5 кГц устройство выдаёт примерно **4,474 тыс. кадров/с вместо 5**, теряя **10,717 %**
временной шкалы строго регулярным образом: **два-три пропущенных отсчёта примерно каждые двадцать**,
около **250 событий пропуска в секунду**. Это не случайная загрузка системы.

Что мы уже исключили:

| Исключено | Основание |
|---|---|
| Наш драйвер | Прямой зонд счётчиков SDK, без нашего ПО в тракте, показывает те же 10,34 % потерь по счётчику |
| Поколение SDK | Идентично на **2.3.21648** (2025) и **2.3.18789** (2021) |
| Размер блока | 15-минутные записи при блоках 50, 500 и 5000 — потери ~10,7169 % в каждом |
| Число каналов | 20, 23, 24, 25, 32, 48 публикуемых ЭЭГ-каналов — потери не меняются, разрыва 24→25 нет |
| Опрос со стороны ПК | Непрерывный повтор вплоть до 75 мс кадры не восстанавливает |
| **Наше приложение целиком** | **Воспроизведено в вашей собственной программе регистрации, при любом числе каналов** |

**Руководство эту частоту декларирует.** §6 «Specification», с. 19: *«Sampling rate 250, 500, 1000,
2000, 5000 Hz (for all channels)»* — 5 кГц на **всех** каналах, с указанной для этой частоты верхней
границей полосы 1650 Гц. То есть речь не о превышении недокументированного предела, а о заявленной
характеристике, которой прибор не соответствует.

Для сравнения, 2 кГц работает чисто: 0 пропущенных строк из 1 799 926 измеренных за 15 минут
(односторонняя верхняя граница 95 % — 1,664 пропущенных строки на миллион).

**Вопросы**
1. Это известный дефект данного поколения усилителей, и есть ли версия прошивки, где он устранён?
2. В чём механизм — планирование USB, упаковщик кадров, внутренняя ступень дециматора?
3. Руководство ограничивает число каналов только на 10 кГц (≤24) и 50 кГц (≤4), а 5 кГц объявляет
   доступной для всех каналов. Существует ли неопубликованное ограничение на 5 кГц, или данный
   экземпляр неисправен?
4. У нас установлен драйвер `McsUsb30` версии **3.3.0.0 (2023)**, новее, чем **3.0 (2012)** из
   комплекта SDK 2025. Какой из них правильный для этого прибора?

**Демонстрация** — `docs/NVX2025-2kHz-5kHz-NaN-Boundary-Validation-2026-08-14.docx` и
соответствующий `.xlsx`; исходные материалы в `R:\dist_2026aug\_build\nvx-validation\boundary-2026-08-14`.

<a id="history-2-nvxsetout--что-в-действительности-означает-аргумент-значения"></a>

## 2. `NVXSetOut` — что в действительности означает аргумент значения?

**SDK** — `NVX.h:490-496`:

```c
/*! Function to set state of output trigger
\param Id - device ID
\param State - state of output trigger (bits 0, 1)     <-- «bits 0, 1» подразумевает 2-битовое поле
*/
NVX_API int WINAPI NVXSetOut(int Id, unsigned char State);
```

**Руководство** — §6, с. 18: *«Synchronization channels 9 / 1»* для NVX52; §1, с. 12: разъём
3,5 мм stereo несёт *«1 input and 1 output triggers»*. **Одна выходная линия** — что совпадает и с
ответом прибора, и с нашими измерениями, и расходится с заголовочным файлом.

**Прибор** — `NVXGetPossibility()` сообщает `OutTriggersCount == 1` (`NVX.h:187`).

**Измерено** — линию поднимает только точное значение **1**. **0, 2 и 3 оставляют её низкой.**
Обратите внимание: у 3 бит 0 установлен, поэтому как битовая маска это не работает ни при каком
толковании.

| `State` | линия |
|---|---|
| 0 | низкий |
| **1** | **высокий** |
| 2 | низкий |
| **3** | **низкий** — хотя бит 0 установлен |

**Вопросы**
1. `State` — это битовая маска, перечисление или количество?
2. Почему 3 не поднимает линию, если бит 0 выбирает выход 0?
3. Не следует ли читать «bits 0, 1» только для моделей, где `OutTriggersCount == 2`?

**Наш код** — `src/nvx/nvxdatathread.cpp:731`, `NVXSetOut(m_deviceId, state & 0x03U)`.
Из-за этого мы переделали параметр из счётчика 0..3 в флажок «включено/выключено».

## 3. Разрядная карта слова `Status` противоречит прибору

**SDK** — `NVX.h:108`, и то же самое в строках 116, 124 и 139:

```c
unsigned int Status; /*!< Digital inputs (bits 0 - 9) + output (bit 10) state + 21 MSB reserved */
```

но `NVX.h:132` — другая структура в том же файле — говорит:

```c
unsigned int Status; /*!< Digital inputs (bits 0, 1) + output (bits 10, 11) state + 20 MSB reserved */
```

**Руководство** — §6, с. 18: *«Synchronization channels 9 / 1»*. §1, с. 12: разъём DB-9F для
*«up to 8 input triggers»* плюс 3,5 мм stereo для *«1 input and 1 output»* — **9 входов и 1 выход**,
ровно столько же сообщает прибор и ровно столько мы измерили. Заголовочный файл — единственный из
трёх источников, где описано десять входов.

**Измерено на NVX-52**, внешней платой на известных контактах:

| | измерено |
|---|---|
| Слово покоя | `0x0000EFFF` — все входы в покое **ВЫСОКИЕ**, поэтому фронт на входе — это переход бита в 0 |
| Входные контакты | биты 6, 7 и 8 для трёх задействованных входов |
| **Чтение состояния выхода** | **бит 9**, а не бит 10 |
| Бит 12 | ни разу не изменялся |

**Руководство и наши измерения согласуются; расходится только заголовочный файл SDK.** Поэтому
вопросы касаются файла, а не прибора.

**Вопросы**
1. Можно ли исправить комментарий к `Status` в `NVX.h` — он описывает десять входов там, где
   руководство, прибор и измерения дают девять?
2. Является ли бит чтения выхода функцией от `InTriggersCount` (то есть сразу над входами), а не
   фиксированным битом 10? Это объяснило бы бит 9 на девятивходовом приборе и примирило бы оба
   комментария.
3. Что представляют собой биты 10–15 на этой модели?

<a id="history-4-режимы-детектирования-входных-триггеров--что-гарантируется"></a>

## 4. Режимы детектирования входных триггеров — что гарантируется?

**SDK** — `NVX.h:68-70` и `NVX.h:471-477`:

```c
#define NVX_TRG_NORMAL (0) /* normal mode */
#define NVX_TRG_FRONT  (1) /* front detection */
#define NVX_TRG_REAR   (2) /* rear detection */
NVX_API int WINAPI NVXSetTriggersMode(int Id, unsigned int Mode);   /* только NVX24, NVX36, NVX52 */
```

**Руководство** — §6, с. 19 описывает каналы синхронизации только так: *«Synchronously with the
issued channel readings; Accuracy ±0.5 / reading»*. Это описание **выборки**, и в нём ничего нет ни
о детектировании фронтов, ни о фиксации (защёлкивании), ни о минимальной длительности импульса. Наш
результат в режиме `REAR` заметно лучше того, что даёт простая выборка, — то есть SDK предоставляет
возможность, которую руководство вообще не описывает.

**Измерено** на линии, которая в покое ВЫСОКАЯ и импульсом уходит в НИЗКИЙ уровень:

| Режим | поведение |
|---|---|
| `NVX_TRG_REAR` | **Фиксирует.** Ловит одиночный импульс **20 мкс** в **95,5 %** случаев и не зависит от частоты — импульс 0,25 отсчёта на 250 Гц пойман 25 раз из 25 |
| `NVX_TRG_NORMAL` | Обычная выборка уровня: доля пойманных равна отношению длительности к периоду дискретизации во всех проверенных точках |
| `NVX_TRG_FRONT` | **Ниже 1 мс на такой линии не ловит ничего — бит вообще не меняется** |

**Вопросы**
1. Какова **гарантированная минимальная длительность входного импульса**? Руководство приводит лишь
   точность выборки ±0,5 отсчёта, при которой импульс 20 мкс вообще не должен ловиться, — а `REAR`
   ловит его в 95,5 % случаев. Описано ли это поведение фиксации где-либо?
2. В режиме `REAR` когда сбрасывается защёлка — каждый кадр или по чтению?
3. Должен ли `FRONT` быть нечувствительным на линии, покоящейся в высоком уровне? Названия
   «front»/«rear» предполагают нарастающий/спадающий фронт; отсчёт ведётся от самого сигнала или от
   внутренней инвертированной копии?
4. Применяются ли эти режимы одновременно ко всем входным контактам?

## 5. Достоверно ли слово `Status` сразу после `NVXStart`?

**Измерено** — **первые 14 кадров после `NVXStart` содержат `Status == 0`**, то есть все входы в
низком уровне, прежде чем слово примет своё значение покоя `0x0000EFFF`. Программа, принимающая
первый кадр за уровень покоя, после этого считает все последующие входные события неактивными.

**Вопрос** — определено ли число кадров после `NVXStart`, в течение которых `Status` недостоверен, и
следует ли их отбрасывать?

<a id="history-6-что-отражает-бит-9--регистр-или-физический-вывод"></a>

## 6. Что отражает бит 9 — регистр или физический вывод?

Короткий вопрос, единственная часть более раннего черновика, пережившая проверку.

Некоторое время мы полагали, что NVX-52 транслирует входной триггер на свой выход, и уже подготовили
это как установленный факт. **Мы отозвали это утверждение до того, как документ попал к вам:**
эффект оказался наводкой на разъёме BNC, который был неплотно вставлен, и исчез после переустановки
разъёма. При заведомо исправном выходном тракте — десять поданных команд прошли 10 из 10 в том же
запуске — 200 импульсов, поданных на вход триггера, не вызвали на выходе ничего. Упоминаем об этом
только на случай, если трансляция является документированной функцией каких-то моделей.

**Остающийся вопрос** — `NVXSetOut` записывает регистр выхода, а бит 9 слова `Status` читается
обратно. Отражает ли это чтение:

1. регистр, записанный ведущим ПО, или
2. фактическое состояние выходного вывода?

Нам предпочтителен вариант (2), поскольку иначе у программы нет способа убедиться, что именно
получает подключённое устройство. Если это вариант (1), драйвер вообще не может обнаружить
залипший или перегруженный выход.

**Вопросы**
1. Какой из двух вариантов сообщает бит 9?
2. Является ли трансляция «вход → выход» функцией какой-либо модели NVX и бывает ли она включена по
   умолчанию?
3. Поддерживается ли `NVXSetMirrorTriggers` на NVX-52 и каков его аргумент?

## 7. Какие вызовы API допустимы во время регистрации?

**Измерено на NVX136** — при запущенном измерении импеданса вызов **`NVXGetVersion` после
`NVXStart` молча прерывает цикл измерения импеданса**: все электроды бесконечно читаются как
`NVX_IMP_INVALID`. Тот же код с запросом версии, перенесённым **до** `NVXStart`, сходится нормально
(16 → 56 → 106 → **129 из 129**). Достаточно одного `NVXGetVersion`; `NVXGetData` в обычном режиме
это переносит.

| Последовательность | измерено электродов |
|---|---|
| версия + заряд батареи **после** `NVXStart` | **0 из 129**, бесконечно |
| только версия, после `NVXStart` | **0 из 129**, бесконечно |
| версия + заряд батареи **до** `NVXStart` | 129 из 129 |

**Вопросы**
1. Какие вызовы безопасно выполнять между `NVXStart` и `NVXStop`?
2. Документировано ли это где-либо и относится ли то же самое к NVX-52?
3. Почему запрос, только читающий данные, прерывает цикл измерения?

## 8. Размер буфера `NVXImpedanceGetData` противоречит заголовочному файлу

**SDK** — `nvx.h:490` (комплект NVX136) описывает приёмный буфер как *«N channels (equal CountEeg
field in t_NVXProperty) + 1 GND»*.

**Измерено** — библиотека 1.5.21743 **отвергает ровно это**:

| буфер | результат |
|---|---|
| 128 слов (`CountEeg`) | `NVX_ERR_PARAM` (-2) |
| **129 слов (`CountEeg + 1`, как описано в заголовке)** | **`NVX_ERR_PARAM` (-2)** |

Мы также обнаружили, что GND — **последнее** слово, а не слово сразу после блока ЭЭГ.

**Вопрос** — какова правильная формула размера буфера и где располагается GND?

## 9. Электрические параметры линий синхронизации — СНЯТО руководством

Оставлено только для протокола, что мы проверяли, и потому что одна строка отсюда подтверждает
внесённое нами изменение.

**Руководство** — §6 «Specification», с. 19:

| | |
|---|---|
| Входные уровни ТТЛ | низкий `Uil > +0,8 В`, `Iil > −2,1 мА`; высокий `Uih > +3,5 В`, `Iih > −0,1 мА` |
| Выходные уровни ТТЛ | низкий `Uol < +0,4 В`, `Iol < −1,6 мА`; высокий `Uoh > +2,8 В`, `Ioh > 0,5 мА` |
| **Состояние по умолчанию** | ***«By default, output trigger channels are High.»*** |
| Изоляция | усиленная, 4000 В / 50 Гц в течение 1 мин; *«The triggers are located on the PC side»* |

**Состояние при включении документировано и совпадает с наблюдаемым.** Мы видели, что выход активен
ещё до того, как ПО что-либо записало, и восприняли это как неожиданность; это заявленное поведение.
Теперь наш драйвер при каждом старте принудительно устанавливает линию в выбранное оператором
состояние, а не оставляет её как есть, — что и является правильной реакцией на документированный
высокий уровень по умолчанию.

**Один остающийся вопрос**
1. Выход выполнен по двухтактной схеме или с открытым коллектором и подтяжкой? Указанное
   `Ioh > 0,5 мА` говорит о том, что он отдаёт ток, но прямо это не сказано, а от этого зависит,
   какую нагрузку допустимо подключать.

## 10. Требование чтения не реже раза в секунду

При подборе размера блока мы обнаружили, что интервалы выдачи, приближающиеся к **одной секунде**,
приводят к потере данных, поэтому мы ограничиваем размер блока (не более 1250 на 1 кГц, не более
2666 на 2 кГц).
⚠ **Отказ происходит молча**: на 2 кГц блок 19000 не давал пропусков, но давал задержку в несколько
секунд, а блок 20000 стал первым случаем с потерей данных — и ни на одном из переходов не появилось
ни одного предупреждения SDK, очереди или счётчика.

**Вопросы**
1. Где именно задано требование к периодичности чтения и каков точный предел?
2. Существует ли код состояния или ошибки, сообщающий о переполнении, вместо молчаливой потери
   кадров?

<a id="history-приложение--что-работает-хорошо-для-равновесия"></a>

## Приложение — что работает хорошо, для равновесия

Это тоже измерено, и претензий у нас нет:

* **Надёжность входа триггера отличная.** 1000 импульсов с частотой 50 Гц на вход при 2 кГц:
  **записано 1065 фронтов из 1065, потерь нет** (5 пробных + 1000 в пачке + 60 ответных).
* **Выход срабатывает быстро.** Полная петля — `NVXSetOut` отпускает линию → внешняя плата
  детектирует → плата выдаёт ответный импульс → вход NVX его фиксирует — проходит с **медианой
  0,000 мс и максимумом 1,5 мс** на 2 кГц, то есть в пределах одного отсчёта 0,5 мс в 77 % случаев.
* **Фиксация в режиме `NVX_TRG_REAR` действительно хороша** — импульсы 20 мкс в 95,5 % случаев,
  независимо от частоты дискретизации.
* Регистрация на 1 кГц и 2 кГц безупречна на 15-минутных записях.

Материалы: `R:\tests\2026-08-18_build_tep-displayfilter\nvx-trigger-validation\nvx-trigger-validation-001.h5`, разбор —
`config/analyze_nvx_trigger_validation.py`.
