<a id="history-1--nvximpedancegetdata-ни-размер-буфера-ни-расположение-слов-не-совпадают-с-заголовком"></a>

## 1. ⚠ `NVXImpedanceGetData`: ни размер буфера, ни расположение слов не совпадают с заголовком

**То, что стоило нам больше всего времени**, поскольку обе половины отказывают либо молча, либо с
кодом ошибки, который ни на что не указывает.

**SDK** — `nvx.h:489-495`:

```c
\param Buffer - pointer to destination buffer values in Ohm
  for N channels (equal CountEeg field in t_NVXProperty) + 1 GND (ground).
NVX_API int NVXImpedanceGetData(HANDLE hDevice, unsigned int *Buffer, unsigned int Size);
```

**Измерено**, библиотека 1.5.21743, `CountEeg = 128`, `CountAux = 8`:

| Предложенный буфер | Результат |
|---|---|
| 128 слов (`CountEeg`) | `NVX_ERR_PARAM` (−2) |
| **129 слов (`CountEeg + 1` — ровно то, что описано в заголовке)** | **`NVX_ERR_PARAM` (−2)** |
| 137 слов (`CountEeg + CountAux + 1`) | `NVX_ERR_OK`, и библиотека записывает **все 137** |

**И показание земли находится не там, где следует из заголовка.** Электроды в воде, земля
подключена, минимальное значение по индексу слова за восемь циклов:

| индекс | показание | что это |
|---|---|---|
| 0…3 | 2,5 / 9,0 / 2,0 / 3,0 кОм | электроды в воде |
| 126, 127 | 999 900 Ом | незадействованные позиции электродов |
| **128** | 999 900 Ом | **AUX 1** — сюда попадает GND у того, кто следует заголовку |
| 129…135 | 999 900 Ом | AUX 2…8, ровно `CountAux` слов |
| **136** | **0 Ом, затем 8000–8500 Ом после установления** | **настоящая GND** |

То есть формат данных — `[EEG(0…CountEeg−1)][AUX(CountEeg…CountEeg+CountAux−1)][GND(CountEeg+CountAux)]`.
Требуемый размер буфера — не причуда, **это и есть раскладка**. Программа, следующая заголовку,
получает `NVX_ERR_PARAM` на каждом вызове; программа, исправившая только размер, публикует AUX 1
как землю — постоянно вне диапазона — и настоящего показания земли не видит вовсе.

**Вопросы**
1. Можно ли исправить заголовок на `CountEeg + CountAux + 1` с GND в последнем слове?
2. Гарантируется ли, что блок AUX не несёт импеданса, или в какой-то конфигурации он значим?
3. Одинакова ли эта раскладка на всех прошивках NVX136, или она следует за `CountAux`?

**Наш код** — `nvx136logic.h:64` `impedanceGndWord()`, `:81` `impedanceReadWords()`;
`nvx136driver.cpp:732`.

<a id="history-2--nvxgetversion-после-запуска-импеданса-молча-прерывает-цикл-измерения"></a>

## 2. ⚠ `NVXGetVersion` после запуска импеданса молча прерывает цикл измерения

**Самое опасное из найденного**, потому что отказ неотличим от попросту неподключённой шапочки.

После исправления буфера вызовы возвращали `NVX_ERR_OK`, а **все электроды бесконечно читались
как `NVX_IMP_INVALID`**. Причиной оказался один-единственный запрос только на чтение, выданный
после запуска:

| Последовательность, то же оборудование, в остальном идентично | измерено электродов |
|---|---|
| без запроса версии/батареи | 16 → 56 → 106 → **129 из 129** примерно за 5 с |
| версия + батарея **после** запуска | **0 из 129**, бесконечно |
| **только версия, после запуска** | **0 из 129**, бесконечно |
| версия + батарея **до** запуска | 16 → 56 → 106 → **129 из 129** |

Достаточно одного `NVXGetVersion`. Об отказе не сообщается ничем: вызов возвращает OK,
последующие `NVXImpedanceGetData` возвращают OK, а данные — это равномерно признак «не
подключено». В обычном режиме регистрации `NVXGetData` тот же запрос переносит.

В **руководстве прикладного программиста NVX** правила порядка вызовов для некоторых функций
есть — про `NVXSetTriggersMode` прямо сказано *«Calling this function before function NVXStart»*
(§1.6.3), — но ничего подобного про запрос версии там нет, как нет и в заголовке NVX136.

**Вопросы**
1. Какие вызовы допустимы между стартом и остановом — в обычном режиме и в режиме импеданса?
2. Почему запрос, только читающий данные, прерывает цикл измерения, а не ставится в очередь и не
   отклоняется?
3. Может ли такой вызов возвращать ошибку вместо молчаливого срыва измерения?

<a id="history-3-неподключённые-электроды-заголовок-говорит-int_max-оборудование--999-900-ом"></a>

## 3. Неподключённые электроды: заголовок говорит `INT_MAX`, оборудование — 999 900 Ом

**SDK** — `nvx.h:487`: *«if electrode not connect, value equal to `NVX_IMP_INVALID` (`INT_MAX`
from `<limits.h>`)»*, при диапазоне измерения от 0 Ом до 120 кОм (`nvx.h:483`).

**Измерено** — незадействованные позиции электродов стабильно читаются как **999 900 Ом**, а не
`INT_MAX`. `INT_MAX` действительно появляется, но в другой ситуации: именно так читаются все
электроды после срыва цикла измерения (см. §2).

В итоге мы вынуждены догадываться о смысле трёх различных значений:

| значение | что мы сейчас предполагаем |
|---|---|
| 0 | этот электрод в текущем цикле ещё не измерялся — это не показание |
| 999 900 Ом | измерено, значение выше диапазона |
| `INT_MAX` (`NVX_IMP_INVALID`) | не измерено / недостоверно |

**Вопросы**
1. Какое значение означает «вне диапазона», а какое — «недостоверно»? Таблица выше — наша догадка.
2. Является ли 999 900 Ом документированным признаком? В заголовке он не встречается.
3. В руководстве программиста NVX (не 136), §1.8.3, сказано, что значения выше 120 кОм
   возвращаются как `INT_MAX`. Отличается ли соглашение NVX136 намеренно?

<a id="history-4--кадры-импеданса-публикуются-в-середине-цикла-и-ещё-не-измерено--это-0-ом"></a>

## 4. ⚠ Кадры импеданса публикуются в середине цикла, и «ещё не измерено» — это 0 Ом

Прибору требуется примерно **750 мс на 32 электрода**, то есть полный цикл на 128 электродов
занимает около 3 с, — но данные доступны заметно чаще. Электроды, до которых текущий цикл ещё не
дошёл, возвращаются как **0 Ом**.

**0 — это не признак отсутствия данных, это наилучший возможный импеданс.** Программа
отображения красит его зелёным. Наблюдалось прямо в записи: обновление в середине цикла дало
`0 0 0 0 0 0` для каналов 1–6, тогда как в предыдущем обновлении на тех же электродах было
1,5–28,5 кОм. Оператор, глядя на шапочку, видит, как каналы каждые несколько секунд «становятся
идеальными». То же делает земля, и, будучи последним словом, появляется дольше всех — из-за чего
её «0 Ом» сначала выглядел как правдоподобное показание земля-земля. Это не так: настоящий
импеданс земли на той шапочке — 8000–8500 Ом.

**Вопросы**
1. Есть ли способ узнать, что цикл завершён, или какие электроды реально содержатся в текущем
   кадре, — счётчик, флаг, признак достоверности по каждому слову?
2. Задуман ли 0 Ом как «ещё не измерено», и если да, можно ли отличить его от настоящего
   показания около нуля?
3. Какова гарантированная частота обновления цикла в зависимости от числа электродов?

*(Мы обходим это, удерживая последнее реальное показание по каждому электроду и повторно публикуя
его, пока прибор не измерит этот электрод снова. Работает, но это догадка о замысле.)*

<a id="history-5-nvxsetmirrortriggers-не-документирована-и-не-поддерживается-нашим-конвертером"></a>

## 5. `NVXSetMirrorTriggers` не документирована и не поддерживается нашим конвертером

**SDK** — `nvx.h:694-695`, объявлены **вообще без блока документации**:

```c
NVX_API int NVXGetMirrorTriggers(HANDLE hDevice, unsigned char *MirrorTriggers);
NVX_API int NVXSetMirrorTriggers(HANDLE hDevice, unsigned char *MirrorTriggers);
```

**Измерено** — наш медиаконвертер отвечает **`NVX_ERR_SUPPORT` (−5)** на `NVXSetMirrorTriggers`,
в том числе при выключении трансляции, то есть при установке состояния, в котором он,
предположительно, и находится.

Сначала это было для нас жёстким отказом: вызов считался фатальным, поэтому **не запускалось
ничего**, а причина попадала только в журнал, которого оператор не видит. Теперь вызов проходит
через помощник, который считает `NVX_ERR_SUPPORT` предупреждением, если оператор просил то
состояние, в котором прибор и так находится, и по-прежнему ошибкой, если он просил саму функцию:
молча вести регистрацию без запрошенной аппаратной настройки означало бы писать не в тех
условиях, которые были заданы.

**Вопросы**
1. Что делает трансляция триггеров — повторяет вход триггера на выходе?
2. Каков аргумент? Тип `unsigned char *` предполагает битовую маску по 8 линиям, но об этом нигде
   не сказано.
3. Какие приборы её поддерживают? Ожидаем ли `NVX_ERR_SUPPORT` от медиаконвертера?
4. Выключена ли она по умолчанию?

**Наш код** — `nvx136driver.cpp:341`.

<a id="history-6-вызовы-связанные-с-батареей-блокируются-на-275-с-и-завершаются-ошибкой"></a>

## 6. Вызовы, связанные с батареей, блокируются на 2,75 с и завершаются ошибкой

**Измерено** — `NVXGetBatteryLevel` и `NVXGetBatteryParameters` **блокируются примерно на 2,75 с и
возвращают `NVX_ERR_FAIL` (−3)**, и в остановленном, и в работающем состоянии, каждый раз. В
сравнении с остальным стартом:

| вызов | время |
|---|---|
| `NVXOpenEx` | **3267 мс** |
| конфигурация устройства/настроек/PLL, семь вызовов | ~280 мс суммарно |
| `NVXStart` | 222–1136 мс |
| `NVXGetVersion` | 48–285 мс |
| **`NVXGetBatteryParameters`** | **2750 мс, затем −3** |

`NVXGetVoltages`, напротив, выполняется за **16–32 мс** и возвращает реальные данные (6,16 В,
28,5 °C), поэтому оценку заряда мы теперь выводим из напряжения холостого хода. Удаление вызова
батареи сократило наш старт с ~7,8 с до **5,0 с**.

**Руководство пользователя** описывает батарейный модуль (NVX136-ACC, 6 В, 8 А·ч) как часть
системы, а §5 предписывает оператору *«Check the battery charge in the "Status Bar" of the
software»* — то есть состояние батареи явно предполагается доступным приложению.

**Вопросы**
1. Откуда следует читать состояние батареи? Из модуля усилителя, а не из медиаконвертера?
2. Почему вызовы батареи блокируются на 2,75 с перед отказом, а не возвращаются сразу?
3. Является ли `NVXGetVoltages` предполагаемым источником и существует ли опубликованная кривая
   «напряжение — заряд» для батареи NVX136-ACC? Наша интерполирована по обобщённой таблице для
   свинцово-кислотной батареи 6 В и проседает под нагрузкой: мы измерили 53 % → 49 % за первую
   минуту регистрации на отдохнувшей батарее.

<a id="history-8-ограничения-по-частоте-и-числу-каналов-проверяются-в-sdk-или-на-стороне-по"></a>

## 8. Ограничения по частоте и числу каналов проверяются в SDK или на стороне ПО?

**Руководство** — §8 «Спецификация» перечисляет частоты дискретизации с соответствующими полосами
и ограничивает верхнюю: **100 кГц только для 64 ЭЭГ-каналов**, далее 50, 25, 10, 5, 2, 1, 0,5 и
0,25 кГц.

**Вопрос** — отклоняется ли запрос, нарушающий это, самим SDK с ошибкой, или он принимается и
молча ухудшается? Мы проверяем это у себя и отказываем в старте, но предпочли бы полагаться на
прибор, если он это уже делает.

<a id="history-приложение--снято-руководством-оставлено-для-протокола"></a>

## Приложение — снято руководством, оставлено для протокола

Пункты, которые мы держали как вопросы, а затем закрыли сами, прочитав документацию:

* **Линии триггеров при включении находятся в ВЫСОКОМ уровне.** §8: *«TTL levels of the output
  synchronization channels are set programmatically by command from the PC. By default, output
  trigger channels are High.»* Наш драйвер теперь при старте принудительно устанавливает линию в
  выбранное оператором состояние, а не оставляет как есть.
* **8 входных и 8 выходных линий триггеров**, DB-9F на вход и DB-9M на выход, с полными уровнями
  ТТЛ (логическая единица на входе +2,0…+5,5 В, гистерезис триггера Шмитта 0,3…1,2 В; на выходе
  ≥3,8 В при −8 мА, ≤0,4 В при 8 мА, суммарный выходной ток ≤±75 мА, длительность перехода ≤5 нс).
* ⚠ **Каналы синхронизации НЕ имеют гальванической развязки от ПК** (§8, «Media converter»). Это
  отличается от NVX-52, у которого триггеры имеют усиленную изоляцию, и это эксплуатационное
  ограничение, о котором надо знать, а не вопрос.
* **Диапазон измерения импеданса электродов** 1–120 кОм ±10 % на 30 Гц; заголовок дополнительно
  указывает, что для любого измерения импеданса должны быть подключены и электрод земли, и
  электрод REF (первый электрод первого слота).

## Что работает хорошо, для равновесия

* Сама регистрация надёжна: десятиминутный сеанс на **25 кГц, 70 ЭЭГ-каналов + триггер, блок
  2500** записан нашим стеком без пропусков, при 13,6 МБ/с по USB.
* `NVXGetVoltages` быстрая и надёжная — хорошая замена API батареи.
* Как только размер буфера и раскладка слов были исправлены, измерение импеданса сошлось
  полностью: 129 электродов из 129, при этом земля показывает живые 8000–8500 Ом, а не
  застрявший максимум.
