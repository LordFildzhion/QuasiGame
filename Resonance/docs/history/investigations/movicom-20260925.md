Status: dated feasibility evidence. No Resonance service was built or deployed. Current proposed scope is in [the Movicom proposal](../../decisions/proposals/movicom.md).

## Supplied implementation

The application is a frozen Python 2.6 program with its application modules in `library.zip` and executable resources. Relevant recovered modules are `signalsource/MoviEEG/api_v2010_12_03_1_03_190/api.py`, `reader.py`, `signalsource/mmapserver.py` and `mmapclient.py`. The frozen `movieeg_ds.exe` calls the reader approximately every 100 ms and writes a two-second memory-mapped ring. `eeg_view.exe` attaches to that ring. The shipped P300 recording parameters specify eight int32 channels and 500 Hz.

`MoviEEG.dll` is x86, version 1.3.190, using cdecl entry points. SHA-256: `196a50b8ab853adfa2f47b4202c946968665780555ddc964f99810c1e1941424`. It imports FTDI D2XX and the x86 `FTChipID.dll`; it does not require the old Python application to acquire.

The 17 exports cover count/handle/open/close/read, version and chip ID, three software filter selectors, and EEPROM user-area access. There is no exposed sample-rate setter, impedance measurement, trigger I/O, per-channel gain or hardware reference selection. EEPROM write exports are not ordinary acquisition controls and were not called.

The Python wrapper establishes the data ABI: **44 packed bytes** per record: int32 sample number at offset 0, double synchronization time at offset 4, eight int32 values at offset 12. Read capacity and return value are in records, not bytes. The major/minor/build version structure is six packed bytes. `movieegGetIDFromHandle` in the Python wrapper accidentally calls the number-based function; the native probe uses the correct export.

The library enumerates the exact FTDI description `Movicom EEG Control`. Enumeration reconstructs its handle storage, so a production broker must not rescan while a saved acquisition handle is in use.

The analog conversion visible in `movieegRead` is:

```
signed24 / 8388607 / 12 * 2051000000
```

The result passes through software filters and is converted to int32. This is consistent with nanovolts from a 2.051 V reference and gain 12, approximately 20.37 nV per ADC count. **That physical-unit interpretation is an inference**, not a recovered calibration certificate or manual. A known analog input must confirm units/polarity before claiming calibrated volts. The default filter selectors are zero/bypass. FrequencyHigh and FrequencyLow accept indices 0–5 and FrequencyReject 0–2, modify in-memory filter state, and do not write device commands. Even an out-of-range selector returns success. Numerical cutoff labels were not established and must not be invented.

The memory-map route would retain the old executable, its 100 ms polling and a ring whose reader infers the write cursor from the maximum sample number. It is usable as a compatibility route, but a poor foundation for a new acquisition service.

## Recovered wire protocol

Recovered from the DLL and checked against live captures:

- FTDI direct interface, 500,000 baud, 8 data bits, no parity, one stop bit, no flow control.
- Start bytes `D1 DD`; stop bytes `D0 DD`.
- Frame length 28 bytes: `DA`, one counter/status byte, one synchronization-tag byte, eight signed big-endian 24-bit channels, one CRC byte.
- Low six bits of the counter/status byte are the sample counter, modulo 64. Upper bits were observed as values 0 and 1 after shifting by six; their meaning remains unknown. Do not label them triggers or electrode-contact quality.
- CRC covers the first 27 bytes including `DA`, initial value FF, reflected polynomial 8C, final XOR FF.
- The parser must retain partial frames, search for a valid CRC after losing alignment, and preserve raw status fields for diagnosis.

The DLL extends the six-bit counter into a 32-bit sample number. That does **not** create a hardware 32-bit counter: a missing multiple of 64 frames can escape modulo detection. At nominal 500 Hz the ambiguity period is 128 ms. Zero detected gaps is therefore a qualified result, not proof of unlimited loss detection. CRC failures, resynchronization, silence, duplicates and resets need separate accounting.

The `st` field is **host synchronization, not an external trigger timestamp**. The DLL periodically sends `D7`, an 8-bit tag and CRC; it stores a Windows performance-counter time and looks it up when the device echoes the tag in frames. The worker sleeps 17 ms between attempts. The direct probes sent no synchronization tags: the received tag remained at the last value, 60, from the old DLL session. A future driver may implement the same tag exchange for clock alignment, but its precision and delay need characterization. No physical trigger output is implied.

Relevant DLL addresses (image base 10000000): read/scaling 100027B0; filter setters 10001270/100012C0/10001310; filter defaults 10001A05; start helper 10001E40; close 10001EE0; serial setup 10003270; enumeration 10003C40; frame CRC 10003EE0; frame reception 10004130; clock-tag worker 10005910.

## Live checks

All trials were sequential and used only this identified amplifier. The initial probes below used no original GUI. The follow-up described later launched the original acquisition/viewer and ran offline classifier training. No live P300 experiment, EEPROM write, unknown hardware command, gain setting or impedance command was launched. Captures verify transport; electrode contact and useful physiological EEG were not assessed.

### Old DLL compatibility

A small native x86 program loaded the unchanged DLLs using the installed FTDI driver. Two ten-second read windows returned 5,102 and 5,101 records, with no reported counter gaps, duplicates or backward jumps. Both closes returned zero. Open took 593 ms and 16,516 ms respectively. These figures include the vendor start path; the two read windows include buffered startup data and are not sample-clock measurements. Reads sometimes delivered 142 records together. Saturation appeared in the initial capture; no saturation code was reinterpreted as an invalid-electrode sentinel.

This establishes that an x86 vendor broker is feasible, while documenting a long reopen delay that needs investigation if this route is chosen.

### Native x64 D2XX, default buffering

Two eight-second windows delivered 3,968 and 3,967 complete valid frames. Typical nonempty-read spacing was about 282.7 ms, with 3,968-byte bursts. The second capture had an initial rejected candidate/23 discarded bytes while finding alignment. Within the accepted sequences there were no detected counter gaps or duplicates.

The default FTDI USB request is 4,096 bytes. Its USB status bytes explain the 3,968 payload-byte bursts. Merely polling more often cannot remove this buffering.

### Native x64, 64-byte USB input requests

Changing the USB input request size before starting reduced median delivery spacing to about 5.0 ms. However, approximately 282 ms stalls still appeared, including at startup. Leaving the 16 ms FTDI latency timer unchanged was not sufficient in these trials.

### Native x64, 64-byte USB input requests and 2 ms latency timer

Two eight-second windows each delivered 4,004 complete valid frames. First data arrived about 4.6 ms after the start write. Median nonempty-read spacing was about 2.50 ms. Maximum spacing was 2.82 and 5.81 ms. There were zero rejected CRC candidates, discarded bytes, detected counter gaps or duplicates; each ended with a partial trailing frame outside the complete-frame count.

A subsequent **30.0025-second** acquisition delivered **15,026 frames**, zero CRC failures, zero discarded/trailing bytes, zero detected modulo-counter gaps and zero duplicates. Median delivery spacing was 2.5047 ms, the 99th percentile after the first second was 2.7070 ms, and maximum spacing was 5.2386 ms. Largest read was 84 bytes, equivalent to three frames.

These are **host delivery intervals**, not analog-input-to-host latency or guaranteed worst-case bounds. They come from a short Python/ctypes probe polling at about 2 ms, not a finished Qt service.

A linear fit of received byte count to host performance-counter time after the first second gave about **500.93 frames/s** in the 30-second trial; the two short optimized trials gave 500.88 frames/s. The supplied software declares 500 Hz. This discrepancy requires a longer independent clock check; do not silently replace the nominal rate with this short-run estimate or promise exact clock synchronization.

The live probe restores the previously read latency timer in its cleanup path. A final independent check confirmed latency **16 ms**, successful open/close, and zero queued bytes at three successive checks over 0.7 seconds. Acquisition is stopped and all probe processes exited.

## Follow-up: KARDi2.dll, original programs and offline drivers

### Why KARDi2.dll is bundled

The application imports `filters/KARDi2.pyc` from `library.zip`. Its docstring identifies it as an implementation of filters from KARDi2.dll. It loads the DLL with ctypes and wraps the **HF**, **BF** and **AF** filter create/configure/process/destroy entry points. Its `customPy2ExeStep` explicitly includes KARDi2.dll in the frozen distribution. This is a real software-filter dependency, not evidence that Movicom acquisition uses a KARDi amplifier or its hardware driver.

`osciloscope/osciloscope.pyc` imports this wrapper. With **Check!** enabled, **Reject 50 Hz** constructs eight `KARDi2.ARFlt(500.0, 50.0)` instances. A selected bandpass builds cascaded second-order `KARDi2.BFlt(FT_BAND_PASS, 2, 500.0, low, hi)` instances. `FFProxy` converts viewer arrays to int32 before calling the DLL, then back to float64. The normal branch uses the application's Python/SciPy filter classes. The Check branch computes a Butterworth/Bessel label but its BFlt call does not pass that choice; do not assume exact filter equivalence from the UI label.

The common `filters/filters.pyc` imports the wrapper unconditionally, so a program can load KARDi2.dll even when it is not actively using the Check filter path. Python 2.6 list-comprehension decompilation produced invalid placeholder expressions; the critical call sites above were therefore checked against Python 2.6 bytecode disassembly (`filter-bytecode.txt`).

The application's KARDi2.dll is x86 version 1.6.0.0, SHA-256 `e55c4c62a879bcbccee299ffba1fd6bc0a9a6b4528986d0d3ec77efc1fab6af0`. It differs from the KARDi2 binary already supplied with Resonance. Do not substitute one for the other. The live `movieeg_ds.exe` module list contained MoviEEG.dll, FTChipID.dll and the installed FTD2XX.dll, with no KARDi2.dll. No KARDi hardware acquisition call was found in the recovered application call sites.

### Original application checks

Before this follow-up, only the recovered source and standalone DLL/protocol probes had been used; the original GUIs had not been run. The follow-up launched unchanged `Mind Controlled Browser/movieeg_ds.exe` and `eeg_view.exe`. The viewer displayed eight traces fed through the original shared-memory route. The final ring snapshot contains 1,000 unique consecutive sample numbers, 69,857 through 70,856, each with eight int32 channels. This verifies operation of the original transport/viewer path, not clean EEG, calibration or physiological quality. The display was initially dominated by large excursions at its default scale.

The viewer opened on the primary display. Attempts to move it using the window-control tool did not complete before the window closed; no further GUI was opened while the user worked on the primary monitor. A future original-GUI test must arrange the secondary display first. No claim is made that Check-mode filtering was exercised interactively.

The original `fisher.exe` then processed `BCI_DEMO_universal/data/learn` with all eight channels and `-t`, with plotting disabled and a new output prefix in the scratch directory. It produced `reference-classifier.ld` (3,911 bytes), printed `invmul test: Ok.`, and had empty stderr. Its own test reported approximately 53% correct; this is only a successful execution/reference artifact, not evidence of useful P300 accuracy or independent validation. The example input files were not overwritten. `learningsession.exe` and `player.exe` were inspected but no new live learning/playback session was conducted.

The pre-existing AppData ring files were backed up and restored. The owned acquisition process was stopped after the viewer closed. A first cleanup stop write without restoring the serial parameters did not stop incoming bytes. Configuring **500,000 baud / 8N1 / no flow control before the stop write** succeeded. Final independent open/close checks reported zero queued bytes at all three observations and latency 16 ms. This reinforces that recovery code must configure the transport before issuing a stop after reopening; process termination alone is insufficient.

### Installer contents and prepared offline package

Read-only extraction of `R:\equipment\Movicom\setup.exe` identified Inno Setup 5.3.10 Unicode and the embedded file `app\drivers\CDM20802_Setup.exe`. Its SHA-256 is `8ba6b18fc9bf0e31d9d00287bf6683b15bf8a4480d3a5a1006f23006896196ae`, identical to the file in the installed application's drivers folder. The application installer and driver installer were not executed.

The bundled driver is FTDI CDM **2.08.02**, dated **2010-07-12**. Its extracted NSIS contents include x86 and AMD64 bus/serial drivers, INF files, catalogs, D2XX DLLs and DPInst executables. The INF supports this device's 0403:6001 identity. Its stated Windows generation extends through Windows 7/Server 2008 R2; prefer the newer working package for the current Windows 10/11 deployment.

Prepared `R:\equipment\Movicom\Offline-driver-FTDI-2.12.36.20-x64.zip` (925,984 bytes), with an adjacent unpacked folder. The contents were exported using PnPUtil from the working local `oem138.inf` and `oem139.inf` packages. Original driver bytes, catalogs and FTDI license text remain unchanged. Both catalog signatures are valid Microsoft Windows Hardware Compatibility Publisher signatures, and SignTool verified membership of both INF files in their catalogs. SHA-256 verification and ZIP round-trip comparison passed for all 14 payload/documentation files.

`Install-driver.cmd` uses Windows PnPUtil to stage/install the two signed packages, writes a local log, preserves error/restart status and does not restart automatically. It must be run as administrator. This package targets Intel/AMD **x64 Windows**; its i386 D2XX DLL is for 32-bit applications on x64, not a complete 32-bit OS driver package. Driver installation on a clean second PC remains untested. This is an offline backup/deployment dependency for the user's amplifier, not a built Resonance service or a claim of general redistribution rights.

## Supporting primary references

FTDI documents the direct D2XX alternative to virtual COM ports in its [interface introduction](https://www.ftdichip.com/Support/Knowledgebase/d2xxintroduction.htm). Its [driver-operation note](https://www.ftdichip.com/Support/Knowledgebase/an232b_03driveroperation.htm) describes the default 4 KiB USB requests and immediate/discarding effect of changing request size. Its [latency note](https://www.ftdichip.com/Support/Knowledgebase/an232b_04adjlatency.htm) describes the 16 ms default and D2XX timer control. Configure these before starting acquisition.

A [published study using this amplifier](https://psyjournals.ru/journals/exppsy/archive/2015_n4/Basyul) independently describes eight channels and 500 Hz, but supplies no SDK, calibration or connector specification. The local wrapper, DLL and measured device remain the main engineering evidence.

FTDI's [official D2XX/CDM download page](https://ftdichip.com/drivers/d2xx-drivers/) lists desktop driver 2.12.36.20 and Windows 10/11 installer support. Microsoft's [PnPUtil examples](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-examples) document export and add/install operations. [innoextract](https://constexpr.org/innoextract/) was used only to inspect/extract the supplied setup without installing it.
